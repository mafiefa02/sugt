# Better Auth: what the library actually supports for this setup

> **Snapshot, not durable documentation.** Every claim below is pinned to **`better-auth@1.6.27`**
> and the package bundles installed on **12 August 2026**. File and line references are to those
> bundles. Treat the whole document as unverified the moment the version moves — particularly the
> four findings that contradict our own docs, which are the reason it exists.

What Better Auth **1.6.27** can and cannot do for the setup described in
[`docs/data-model.md`](../data-model.md), [ADR-0011](../adr/0011-supabase-and-better-auth.md) and
[ADR-0013](../adr/0013-people-are-added-in-the-tool-and-their-role-is-write-once.md). This
establishes what is possible; it decides nothing. The auth architecture is a separate ticket.

## The findings that contradict the documents

Four. The first three are in one sentence of `data-model.md` each. What held is listed at the
end of this section, because ADR-0013's central mechanism is among it.

### A. `better_auth` tables cannot be "generated by the CLI, never hand-edited"

`data-model.md` line 70-71 says the four core tables are "Generated by the Better Auth CLI,
never hand-edited." Both halves fail, for three independent reasons.

**The generator only ever emits `pgTable`.** The Drizzle generator builds each table as

```js
const schema = `export const ${modelName} = ${databaseType}Table("${convertToSnakeCase(modelName, adapter.options?.camelCase)}", {
```

— `auth@1.6.27 → dist/index.mjs:687`. `databaseType` is `"pg" | "mysql" | "sqlite"`, so for
Postgres the output is always `pgTable(...)`. The import line is assembled from a fixed list
(`dist/index.mjs:811-826`) that pushes `${databaseType}Table`, `text`, `timestamp, boolean`
and the like. **The string `pgSchema` does not occur anywhere in the CLI bundle** (`grep -c
pgSchema` over `auth@1.6.27 → dist/index.mjs` returns 0). There is no config key, no flag and
no code path that produces a schema-qualified table.

**`auth migrate` refuses the Drizzle adapter outright.** `auth@1.6.27 → dist/index.mjs:7099`
is `if (db.id !== "kysely")`, and at line 7114-7115:

> The migrate command only works with the built-in Kysely adapter. For Drizzle, run
> `npx auth generate` to create the schema, then use Drizzle's migrate or push to apply it.

So there is no "migrate into a named schema" for this stack at all; there is no migrate.
drizzle-kit applies the schema, not Better Auth. (`https://www.better-auth.com/docs/adapters/drizzle`
tells you to run `npx auth@latest generate` then `npx drizzle-kit generate`, consistent with this.)

**The one place Better Auth does understand a Postgres schema is the Kysely path only.**
`better-auth@1.6.27 → dist/db/get-migration.mjs:99-125` runs `SHOW search_path`, takes the
first entry, defaults to `public`, and logs `Using schema '<x>' (from search_path)`. That is
the migration builder behind `auth migrate`. The docs page
`https://www.better-auth.com/docs/concepts/database` states "The migrate command supports
non-default schemas. It automatically detects your `search_path` configuration and creates
tables in the correct schema" — true, and irrelevant here, because that command exits before
doing anything when the adapter is Drizzle.

**What does work.** The adapter never builds a table-name string. `getSchema(model)`
(`@better-auth/drizzle-adapter@1.6.27 → dist/index.mjs:89`) looks the model up as a key in the
schema object you pass and hands the Drizzle table object straight to `db.select().from(...)`:

```js
function getSchema(model) {
  const schema = config.schema || db._.fullSchema;
  ...
  const schemaModel = schema[model];
```

A table built with `pgSchema("better_auth").table("user", …)` therefore works at runtime with
no adapter change — Drizzle emits `better_auth."user"` itself. The `better_auth` schema is
achievable. It is achievable by **hand-editing or hand-writing the Drizzle table objects**,
which is exactly what `data-model.md` says will not happen.

`DrizzleAdapterConfig` in full (`@better-auth/drizzle-adapter@1.6.27 → dist/index.d.mts`):
`schema?` (the Drizzle schema _object_, not a Postgres schema name), `provider` (required,
`"pg"` here), `usePlural?`, `debugLogs?`, `camelCase?` (default `false`, snake_case names),
`transaction?` (**default `false`**). There is no schema-name option and no per-table schema
option.

Note also `modelName` (the `user: { modelName: … }` option) is not an escape hatch: with the
Drizzle adapter a model name is a **key into the schema object**, not SQL, so
`modelName: "better_auth.user"` would look for a schema key of that name and throw
`The model "…" was not found in the schema object`.

### B. The admin plugin adds four columns to `user`, not one

ADR-0013's consequences list budgets for "a `banned` column on `better_auth.user`". The
plugin's schema is (`better-auth@1.6.27 → dist/plugins/admin/schema.mjs`, verbatim):

| Table     | Column           | Type      | Attributes                                               |
| --------- | ---------------- | --------- | -------------------------------------------------------- |
| `user`    | `role`           | `string`  | `required: false`, `input: false`                        |
| `user`    | `banned`         | `boolean` | `defaultValue: false`, `required: false`, `input: false` |
| `user`    | `banReason`      | `string`  | `required: false`, `input: false`                        |
| `user`    | `banExpires`     | `date`    | `required: false`, `input: false`                        |
| `session` | `impersonatedBy` | `string`  | `required: false`, `input: false`                        |

Confirmed by `https://www.better-auth.com/docs/plugins/admin`.

`role` is the one that matters. The plugin registers its **own**
`databaseHooks.user.create.before` that writes it on every user creation
(`dist/plugins/admin/admin.mjs:26-32`):

```js
user: { create: { async before(user) {
  return { data: { role: options?.defaultRole ?? "user", ...user } };
} } },
```

So adopting the admin plugin puts a column named `role` on the identity table, defaulted to
`"user"`, sitting next to `person.role` which is write-once and means Staff or Teaching Team.
ADR-0013's "one writer, one direction" discipline was written for `banned` alone and now has
three more columns and a second `role` in scope. `impersonatedBy` on `session` lands in
`better_auth.session`, not `public.session`, so it collides with nothing.

The plugin composes cleanly with a custom schema and with `additionalFields`: its schema is
merged through `mergeSchema(schema, opts.schema)` (`dist/plugins/admin/admin.mjs`), plugin
`databaseHooks` are pushed onto the same hook list as the app's (see finding C and question 3), and it reaches the
database only through `internalAdapter`, which goes through the adapter you configured. It
never assumes `public`.

### C. `person_id` as a generated `additionalField` produces a file that does not compile, and the wrong column type

`data-model.md` line 146-154 declares `person_id uuid unique references public.person (id)`
via `user.additionalFields`, with the foreign key added by a follow-up migration "since the
generated schema will not write a cross-schema reference". The conclusion is right; the
mechanism is worse than "will not write".

`additionalFields` is typed `{ [Key in Exclude<string, Keys | "id">]: DBFieldAttribute }`
(`@better-auth/core@1.6.27 → dist/types/init-options.d.mts:133`). `DBFieldAttribute` accepts
`type`, `required`, `returned`, `input`, `defaultValue`, `onUpdate`, `transform`,
**`references`**, `unique`, `bigint`, `validator`, `fieldName`, `sortable`, `index`
(`@better-auth/core@1.6.27 → dist/db/type.d.mts:31-114`). The docs page for extending the core
schema lists only `type`/`required`/`defaultValue`/`input`/`returned` — the type definition is
the fuller and authoritative list.

**There is no `uuid` type.** `DBFieldType` is
`"string" | "number" | "boolean" | "date" | "json" | "string[]" | "number[]" | LiteralString[]`
(`dist/db/type.d.mts:29`). `type: "string"` on Postgres generates `text('person_id')`
(`auth@1.6.27 → dist/index.mjs`, `dbTypeMap.string.pg`). A `text` column cannot carry a
foreign key to `person.id uuid` — Postgres requires the referencing and referenced types to
match. The follow-up migration in `data-model.md` adds a `uuid` column; the generator produces
`text`. These are different columns.

There is one narrow path to `uuid`: `getType` returns `uuid('<name>')` when
`field.references?.field === "id"` **and** `advanced.database.generateId === "uuid"` — but
that option also switches Better Auth's own `user.id`/`session.id`/etc. to `uuid`, which is a
whole-schema decision, not a per-column one.

**Declaring `references` breaks the generated file.** If `person_id` carries
`references: { model: "person", field: "id" }`, the generator emits

```js
.references(()=> ${getModelName(attr.references.model)}.${getFieldName(...)}, { onDelete: 'cascade' })
```

(`auth@1.6.27 → dist/index.mjs`, the field-emission branch). `getModelName("person")` returns
`"person"` unchanged, because `person` is not in Better Auth's table registry
(`@better-auth/core@1.6.27 → dist/db/adapter/get-model-name.mjs` — unknown models fall through
to `return usePlural ? \`${model}s\` : model`). The output references an identifier `person`that`auth-schema.ts` never defines. TypeScript will not compile it. The generated file is
hand-edited or it is broken — a third independent reason the "never hand-edited" claim cannot
stand.

**A tension for the architecture ticket, not resolved here.** `data-model.md` line 990-995
says drizzle-kit leaves `better_auth.user.person_id` alone "because neither is in its
snapshot". But the Drizzle adapter reads columns off the table object you give it (finding A), so
`person_id` has to be present in the Drizzle table for Better Auth to read or write it — at
which point it _is_ in drizzle-kit's snapshot and the stated reason stops applying. Whether
`person_id` should be Drizzle-managed or hand-managed is an architecture decision; this note
only records that the current reasoning assumes both.

### D. Revocation is immediate only while `session.cookieCache` stays disabled

ADR-0013 line 44 says `/admin/ban-user` "blocks sign-in and revokes existing sessions in one
call". True in 1.6.27, with a condition the ADR does not state.

`banUser` (`better-auth@1.6.27 → dist/plugins/admin/routes.mjs:506-539`) sets `banned: true`,
`banReason`, `banExpires`, then at line 538:

```js
await ctx.context.internalAdapter.deleteUserSessions(ctx.body.userId);
```

The session **rows are deleted**. Sign-in is blocked by a different mechanism: the plugin's
`databaseHooks.session.create.before` (`dist/plugins/admin/admin.mjs:33-49`) reads the user,
clears an expired ban if `banExpires` has passed, and otherwise throws
`APIError.from("FORBIDDEN", { message: opts.bannedUserMessage, code: "BANNED_USER" })`. This
fires on every session creation, including the one at the end of the OAuth callback — so a
banned Google account cannot get a new session either.

Nothing checks `banned` per request. Enforcement between sign-ins is purely "the session row
is gone". That is immediate **only if reading a session touches the database**. With
`session.cookieCache.enabled: true`, `getSessionFromCtx` verifies the signed session-data
cookie and returns it without a database read
(`better-auth@1.6.27 → dist/api/routes/session.mjs:87-110`). A banned user's browser keeps a
valid session until the cache expires — `cookieCache.maxAge` defaults to 5 minutes.

`cookieCache.enabled` defaults to **`false`** (`@better-auth/core@1.6.27 →
dist/types/init-options.d.mts:861-864`), so out of the box revocation is immediate. Turning
cookie caching on — a normal performance move on Vercel — silently reopens a window on a
Staff-only publishing surface. Escape hatches exist (`?disableCookieCache`,
`cookieCache.version` as a function, `getAuthoritativeSessionFromCtx`), but they are opt-in
per call site.

`banExpires` is `undefined` when `banExpiresIn` is omitted and no `defaultBanExpiresIn` is
set, which is a permanent ban. That matches ADR-0013's intent.

### And what held

Four contradictions, above. These claims were tested the same way and are **true** at 1.6.27:

- **ADR-0013 line 13: "an uninvited Google account cannot create a `user` row at all."**
  Holds, and holds even with the adapter's `transaction: false` default, because
  `createWithHooks` runs every `create.before` hook _before_ it calls `adapter.create` — a
  throw never reaches an insert. Mechanism in question 3 below.
- **`data-model.md` line 155: the hook "looks up `person` by lowercased email."** Matches the
  library exactly: Better Auth lowercases the address before the hook sees it, so
  `where lower(email) = $1 and active` is the correct query.
- **ADR-0013 line 40: the hook "fires before a user row is created … a returning sign-in
  creates a _session_, not a user, so the hook never runs again."** Correct, and it is exactly
  why the ban path is needed. `data-model.md` line 118 says the same thing.
- **ADR-0011 line 62-64 and ADR-0013's premise that the invite list gates every account.** No
  code path in the package creates a `user` row without passing through the hook — verified
  across all nine call sites, enumerated under question 6.
- **`data-model.md` line 153-154: "the generated schema will not write a cross-schema
  reference."** True. The reason is sharper than stated — see finding C.
- **ADR-0013 line 44: `/admin/ban-user` "blocks sign-in and revokes existing sessions in one
  call."** True, with the condition in finding D.

## 1. The Drizzle adapter against a non-public schema

Covered in full above. In short, for 1.6.27:

- **Runtime: yes.** Pass `pgSchema("better_auth").table(...)` objects in `drizzleAdapter(db, {
provider: "pg", schema })`. The adapter is schema-agnostic by construction.
- **`auth generate`: no.** It emits `pgTable` only, and knows nothing about `pgSchema`.
- **`auth migrate`: not applicable.** It refuses any non-Kysely adapter.

Peer-range check, from `better-auth@1.6.27`'s `package.json`: `drizzle-orm: ^0.45.2` (catalog
has `^0.45.2` — exact match), `drizzle-kit: >=0.31.4` (catalog has `^0.31.10` — satisfied).

One adapter default worth recording because `data-model.md` describes Supavisor transaction
mode: `transaction` defaults to `false`
(`@better-auth/drizzle-adapter@1.6.27 → dist/index.mjs:580`,
`transaction: config.transaction ?? false ? … : false`). `createOAuthUser` wraps its user and
account inserts in `runWithTransaction`
(`better-auth@1.6.27 → dist/db/internal-adapter.mjs:75-93`), which is a no-op without it — a
failed account insert leaves an orphan `user` row. This does not affect finding C's rejection claim
(the hook runs before any insert), but it is a real default.

## 2. `user.additionalFields` carrying `person_id`

Covered in finding C. What is true regardless of the generator:

- `additionalFields` can declare the field, and the field is a first-class column: it is in
  the create payload, it reaches `databaseHooks`, and it is readable off the session user.
- `input: false` is the flag that stops a client supplying it. On the OAuth path,
  `parseAdditionalUserInputFromProviderProfile`
  (`better-auth@1.6.27 → dist/db/schema.mjs:116-127`) explicitly skips any field with
  `input === false` before parsing the provider profile, so Google cannot inject a
  `person_id` claim.
- The generated column type for `type: "string"` is `text`, not `uuid`.
- A cross-schema `references` cannot be expressed: the generator resolves the referenced model
  through Better Auth's own registry, and `public.person` is not in it.

Better Auth itself never issues DDL on the Drizzle path, so a hand-written
`alter table better_auth."user" add constraint … references public.person (id)` is invisible
to it. What it is _not_ invisible to is drizzle-kit — see the tension noted in finding C.

## 3. `databaseHooks.user.create.before`

**Exact signature**, from `@better-auth/core@1.6.27 → dist/types/init-options.d.mts:1134-1146`:

```ts
databaseHooks?: {
  user?: {
    create?: {
      before?: (
        user: User & Record<string, unknown>,
        context: GenericEndpointContext | null
      ) => Promise<boolean | void | { data: Optional<User> & Record<string, any> }>;
      after?: (
        user: User & Record<string, unknown>,
        context: GenericEndpointContext | null
      ) => Promise<void>;
    };
    ...
```

Two arguments. `context` is nullable — it is `null` when there is no request in flight, so a
hook that dereferences `context.context` will throw on server-side calls.

**The email is already lowercased when the hook sees it.** Both
`createOAuthUser` and `createUser` spread `email: user.email?.toLowerCase()`
(`better-auth@1.6.27 → dist/db/internal-adapter.mjs:75-100`), and `handleOAuthUserInfo` passes
`userInfo.email.toLowerCase()`. `data-model.md`'s "looks up `person` by lowercased email"
matches the library exactly, and `where lower(email) = $1 and active` is the right query.

**No user row is created, and the mechanism is order, not rollback.** `createWithHooks`
(`better-auth@1.6.27 → dist/db/with-hooks.mjs`) runs every registered `create.before` hook
_first_ and only then calls `adapter.create`. A throw never reaches the insert. ADR-0013's
central claim — "an uninvited Google account cannot create a user row at all" — **holds**, and
holds even with `transaction: false`.

**Throw; do not return `false`.** Returning `false` makes `createWithHooks` return `null`
(`dist/db/with-hooks.mjs:17`, `if (result === false) return null;`), after which
`createOAuthUser` immediately reads `createdUser.id` (`dist/db/internal-adapter.mjs:86`) and
dies with a `TypeError`. That still produces no user row, but by accident and with an
unusable error. The documented rejection mechanism is throwing:
`https://www.better-auth.com/docs/concepts/database` has a "Throwing Errors" section with
`throw new APIError("BAD_REQUEST", { message: "…" })`.

**What the end user sees in the browser.** For a Google sign-in the chain is:

1. The hook throws. `handleOAuthUserInfo`'s `try/catch` around `createOAuthUser`
   (`better-auth@1.6.27 → dist/oauth2/link-account.mjs:116-123`) catches it. If it is an
   `APIError` it returns `{ error: e.message, data: null }`; anything else returns
   `{ error: "unable to create user", data: null }`.
   `APIError`'s `message` **is** `body.message` — `super(body?.message, …)` in
   `better-call@1.4.0 → dist/error.mjs:97-113`.
2. The callback route sees `result.error`, logs it, and calls
   `redirectOnError(c, resolvedErrorURL, result.error.split(" ").join("_"))`
   (`better-auth@1.6.27 → dist/api/routes/callback.mjs:162-164`).
3. `redirectOnError` (`dist/oauth2/errors.mjs`) throws a redirect to
   `<errorURL>?error=<code>`.

So it is **a redirect, not a 500, and no stack trace reaches the browser**. Concretely:

| Hook throws                                                        | Browser lands at                          |
| ------------------------------------------------------------------ | ----------------------------------------- |
| `new APIError("FORBIDDEN", { message: "Not on the invite list" })` | `<errorURL>?error=Not_on_the_invite_list` |
| `new Error("whatever")`                                            | `<errorURL>?error=unable_to_create_user`  |

`errorURL` resolves to, in order: the `errorCallbackURL` passed to `signIn.social`
(`dist/api/routes/sign-in.mjs:33`), else `options.onAPIError.errorURL`, else
`<baseURL>/error` (`dist/api/routes/callback.mjs:32,55`). The built-in `/error` page renders a
styled HTML page reading `?error` and `?error_description` from the query string
(`dist/api/routes/error.mjs:363-364`), and `onAPIError.customizeDefaultErrorPage` themes it.

The practical consequence for a message the user should read: it arrives as an underscored
query parameter, not as prose, and only when an `APIError` is thrown. `error_description` is
not populated on this path — `redirectOnError`'s description argument is not supplied here.

One more trap on the built-in page: it validates the code against `/^['A-Za-z0-9_-]+$/` and
falls back to `UNKNOWN` on any other character (`dist/api/routes/error.mjs:365`). A thrown
message containing a full stop, comma or colon therefore renders as `UNKNOWN` rather than the
text that was written. A custom `errorCallbackURL` avoids this entirely, since the app reads
`?error` itself.

**Hook ordering.** Plugin `databaseHooks` are pushed onto the list first, the app's
`options.databaseHooks` last (`better-auth@1.6.27 → dist/context/helpers.mjs:22-46`). So with
the admin plugin installed, the plugin's `role: "user"` default is applied before the app's
invite-list hook runs, and the app's hook can still throw and abort.

## 4. The admin plugin

Columns and ban semantics are in findings B and D above. The remaining answers:

- **Composes with a custom schema:** yes. Its schema is declared as field additions merged via
  `mergeSchema`, and every write goes through `internalAdapter` → the configured adapter. It
  contains no SQL and no schema qualification.
- **Composes with `additionalFields`:** yes, they are independent field maps on the same model.
- **Revocation ends existing sessions:** yes — `deleteUserSessions` deletes the rows, and the
  ban check on `session.create.before` stops a new one being minted. Immediate, subject to the
  `cookieCache` condition in finding D.
- **`/admin/create-user` runs the app's create hook.** It calls
  `ctx.context.internalAdapter.createUser` (`dist/plugins/admin/routes.mjs:194`), which is
  `createWithHooks`. A People screen that provisioned accounts through the plugin would still
  pass through the invite-list gate.
- Every admin endpoint is behind `adminMiddleware` and a `hasPermission` check against
  `adminRoles` (default `["admin"]`) or `adminUserIds`; which of those `better_auth.user.role`
  carries is an architecture decision, and it is the second `role` from finding B.

## 5. Next.js 16 App Router integration

The repo is on `next: 16.2.12` (catalog). `better-auth@1.6.27`'s peer range is
`next: "^14.0.0 || ^15.0.0 || ^16.0.0"`, optional — **Next 16 is in range.** React peer is
`^18.0.0 || ^19.0.0`; catalog has 19.2.4.

**Route handler.** `app/api/auth/[...all]/route.ts`:

```ts
import { auth } from "@/lib/auth";
import { toNextJsHandler } from "better-auth/next-js";
export const { GET, POST } = toNextJsHandler(auth);
```

(`https://www.better-auth.com/docs/integrations/next`.) The implementation actually exports
`GET, POST, PATCH, PUT, DELETE` from one handler
(`better-auth@1.6.27 → dist/integrations/next-js.mjs`), so the destructure can take more than
the two the docs show.

**`nextCookies()` plugin**, from `better-auth/next-js`, **must be last in the `plugins`
array**. The library warns when a plugin declaring `hooks.after` sits after it, because those
hooks "may set cookies that are not forwarded to the framework cookie store"
(`warnIfCookiePluginNotLast`, `dist/integrations/cookie-plugin-guard.mjs`). The admin plugin
declares `hooks.after`, so with both installed the ordering is load-bearing rather than
cosmetic. It also detects
RSC renders (`RSC: 1` header without `next-action`) and skips session refresh there, because
Next cannot set cookies during an RSC render.

**Reading a session in a Server Component:**

```ts
import { headers } from "next/headers";
const session = await auth.api.getSession({ headers: await headers() });
```

**Protecting routes.** The current recommendation is **auth checks in each page/route, not
middleware**. The docs state that `getSessionCookie()` checks only for the cookie's existence
and does "not validate it", and that "you must always validate the session on your server for
any protected actions". Middleware is presented as an optimistic redirect, not a gate. Version
notes on the same page: Next 16+ supports proxy with the Node runtime; 15.2.0+ enables the
Node runtime in middleware; 13–15.1.x are Edge-only and therefore limited to cookie-existence
checks.

## 6. Google as the only social provider, and paths that bypass the create hook

**Minimal config** (`https://www.better-auth.com/docs/authentication/google`):

```ts
socialProviders: {
  google: { clientId: process.env.GOOGLE_CLIENT_ID!, clientSecret: process.env.GOOGLE_CLIENT_SECRET! },
}
```

Notable options on `GoogleOptions` (`@better-auth/core@1.6.27 →
dist/social-providers/google.d.mts:33-51`): `hd` — the Google Workspace hosted domain. It is
sent as the `hd` authorization hint **and enforced against the verified `hd` claim on the way
back** (`dist/social-providers/google.mjs:103,109-110`); `hd: "*"` requires any Workspace
domain. Sign-in is rejected when the claim is missing or does not match. That is a second,
independent gate available alongside the invite list — it is a domain filter, not a list, so
it does not replace one.

Also available per provider: `disableSignUp`, `disableImplicitSignUp` (requires
`requestSignUp: true` on the sign-in call to create anyone), `mapProfileToUser`,
`overrideUserInfoOnSignIn`, `accessType`, `prompt`, `display`
(`@better-auth/core@1.6.27 → dist/oauth2/oauth-provider.d.mts:76-193`).

### Is there any path to a `user` row that skips the create hook?

**No — not in 1.6.27.** Every user-creating call site in the package goes through
`internalAdapter.createUser` or `internalAdapter.createOAuthUser`, and both are
`createWithHooks` (`better-auth@1.6.27 → dist/db/internal-adapter.mjs:75-100`). The complete
list of call sites, from a grep over `better-auth@1.6.27 → dist/`:

| Path                              | Call site                                      | Reachable here?                                                                        |
| --------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------- |
| OAuth sign-in (Google)            | `oauth2/link-account.mjs:97` `createOAuthUser` | yes                                                                                    |
| Email/password sign-up            | `api/routes/sign-up.mjs:221`                   | route is mounted but 400s unless `emailAndPassword.enabled`, which defaults to `false` |
| Admin plugin `/admin/create-user` | `plugins/admin/routes.mjs:194`                 | only if the admin plugin is added                                                      |
| Magic link                        | `plugins/magic-link/index.mjs:160`             | plugin not planned                                                                     |
| Email OTP                         | `plugins/email-otp/routes.mjs:414`             | plugin not planned                                                                     |
| Phone number                      | `plugins/phone-number/routes.mjs:335`          | plugin not planned                                                                     |
| Anonymous                         | `plugins/anonymous/index.mjs:47`               | plugin not planned                                                                     |
| SIWE                              | `plugins/siwe/index.mjs:175`                   | plugin not planned                                                                     |
| Test helper                       | `plugins/test-utils/db-helpers.mjs:5`          | tests only                                                                             |

No code path calls `adapter.create({ model: "user", … })` directly. Every one of the above is
gated by the same hook, so adding a plugin later does not silently open a door — though each
plugin does add its own columns and endpoints.

**Account linking does not create users.** In `handleOAuthUserInfo`, the linking branch runs
only when `findOAuthUser` already returned a row, and it creates an `account` row via
`internalAdapter.linkAccount` — never a `user`
(`better-auth@1.6.27 → dist/oauth2/link-account.mjs:19-50`). `findOAuthUser` matches on
`(accountId, providerId)` first and falls back to a lookup by lowercased email
(`dist/db/internal-adapter.mjs:431-471`). With Google as the sole provider, the only thing
this can do is attach a second Google `account` row to an existing, already-invited user.

Relevant defaults, since they govern that branch
(`@better-auth/core@1.6.27 → dist/types/init-options.d.mts:939-1011`):
`account.accountLinking.enabled` defaults **`true`**; `disableImplicitLinking` defaults
`false`; `requireLocalEmailVerified` defaults `true`, and its doc comment says it exists so
"an attacker who pre-registers an unverified account at a victim's email cannot have the
victim's OAuth identity linked into the attacker-owned row"; `trustedProviders` defaults to
empty; `allowDifferentEmails` defaults false.

**Email verification does not create users.** The `emailVerification` path on OAuth sign-up
runs _after_ `createOAuthUser` has returned a user (`dist/oauth2/link-account.mjs:104-112`);
`/verify-email` updates an existing row. There is no user-creating verification path.

**Where the real hole is, and it is not the library.** The hook gates every route Better Auth
serves. It does not gate `INSERT INTO better_auth."user"` from the Supabase SQL editor, from
`@sugt/db`, or from a seed. `person` is the invite list only for traffic that goes through
Better Auth's API.
